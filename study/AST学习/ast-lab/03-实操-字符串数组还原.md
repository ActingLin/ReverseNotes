# 实操 03：字符串数组还原（反混淆的主战场）

> **配套实例**：`examples/06-string-array.js`、`examples/07-shift-array.js`
> **读完这篇你会**：还原 obfuscator.io 的字符串数组（含数组位移），
> 掌握"求值工厂"这个通用大杀器，理解**为什么"让机器执行"比"人脑推理"可靠**。
> **前置**：读完《01》《02》，理解 exit、作用域和引用计数。

---

## 1. 认识对手：obfuscator.io 的三件套

[obfuscator.io](https://obfuscator.io)（javascript-obfuscator）是 GitHub 上
最流行的开源 JS 混淆器。它的招牌手法是"字符串数组"：

```js
var _0x3f2a = ['log', 'hello world', 'length', 'charAt'];   // ① 大数组
function _0x5e1b(_0x2c) {                                    // ② 取值函数
    return _0x3f2a[_0x2c];
}
console[_0x5e1b(0)](_0x5e1b(1));                             // ③ 索引调用
```

**三件套**：大数组（藏字符串） + 取值函数（按索引取） + 索引调用（用索引代替字符串）。

### 为什么这招有效？

- 代码里再也搜不到 `'log'`、`'hello world'` 这些关键词
- 你看代码时，满眼都是 `_0x5e1b(0)`、`_0x5e1b(1)`，逻辑完全不可读
- 手工一个个查表？几百个字符串，查到崩溃

### 我们的破解思路（先想清楚再写代码）

目标：把 `_0x5e1b(0)` 替换成 `'log'`。

问题是 `_0x5e1b` 返回什么。答案其实**就在代码里**：
数组内容 + 函数逻辑都写着呢，只是**人懒得算**。

> **核心思想：把函数抄下来，让机器算。**

```
收集（数组 + 函数） → 求值（拿到明文） → 替换（调用点 → 字面量） → 清理（删垃圾）
```

这四步流水线，就是所有字符串数组还原器的骨架。

## 2. 复原第一步：收集与求值（`examples/06-string-array.js`）

### 2.1 用"求值工厂"把死代码变成活函数

```js
const factory = new Function(`
    ${arrayCode}      // var _0x3f2a = ['log', ...]
    ${fnCode}         // function _0x5e1b(_0x2c) { return _0x3f2a[_0x2c]; }
    return ${decodeFnName};
`);
const decodeFn = factory();     // 现在 decodeFn 是一个真的、可调用的函数
```

**为什么用 `new Function` 而不是直接 `eval`？**（这是个真实的坑）

```js
// ✗ 有问题的写法
eval(fnCode);
```

在非严格模式下，"直接 eval" 里的 `var` / `function` 声明会落进
**"调用 eval 的那个函数"的作用域** —— 也就是落进你的 visitor 回调函数里。
结果：出了这个回调，`_0x5e1b` 就消失了，后面没法用。

`new Function(...)` 创建的函数拥有**独立的作用域**，
我们把数组声明、函数定义都塞进去，最后 `return` 出函数本身。
干净、无副作用、不污染当前环境。

### 2.2 替换调用点（带安全阀）

```js
traverse(ast, {
  CallExpression(path) {
    if (!t.isIdentifier(path.node.callee, { name: decodeFnName })) return;  // 是它
    if (!t.isLiteral(path.node.arguments[0])) return;                       // 参数是字面量
    let value;
    try {
      value = decodeFn(path.node.arguments[0].value);   // 算！
    } catch (e) { return; }                             // ★ 算不出来就跳过
    path.replaceWith(t.valueToNode(value));
  }
});
```

**两个必要条件，缺一不可**：

| 条件 | 为什么 |
|------|-------|
| 调用的确实是解密函数 | 别把 `foo(0)` 也替换了 |
| 参数是**字面量** | 参数是变量时，值运行时才知道，静态算不了 |

**`try-catch` 是必需品不是装饰品**：解密函数可能引用 `window`、`document`
（Node 环境没有），一跑就抛异常。**吞掉异常、跳过这个点**，
总比整个脚本崩掉强。

### 2.3 清理：为什么这里要写"循环"

替换完成后，数组和函数都没人用了，该删。但**只跑一轮删不干净**：

```
遍历顺序（按源码）：数组声明 → 函数声明 → 调用点
                    ↑ 这里看：函数还在引用我，跳过
                                 ↑ 这里：删掉函数（但本轮已经走过数组了）
```

结果数组漏了。解法是**跑多轮，直到某一轮"什么都没删"**：

```js
while (true) {
  let removed = 0;
  traverse(ast, { /* 删无引用声明 */ });
  if (removed === 0) break;      // 到达固定点，收工
}
```

> **固定点迭代（fixed-point iteration）**是所有反混淆脚本的标配。
> 原因：每次变换都可能"制造新的机会"（删了一个函数，它引用的东西才变成无引用）。
> 反复跑到结果稳定，才叫处理完。
>
> 顺带一提，每轮开头要 `path.scope.crawl()` 刷新作用域缓存——
> 这是《02》里踩过的坑。

### 2.4 效果

```
还原前：console[_0x5e1b(0)](_0x5e1b(1));
还原后：console.log("hello world");
```

## 3. 真正的难点：数组位移（`examples/07-shift-array.js`）

### 3.1 为什么"照 06 的做法"会全错

你兴冲冲地拿 06 的脚本去跑真实网站代码，结果**全错**。
因为真实混淆多了一手：

```js
var _0x4e2b = ['hello world', 'log', 'length'];
(function(_0x1a, _0x2b) {                    // ← 位移 IIFE
    var _0x3c = function(_0x4d) {
        while (--_0x4d) {
            _0x1a['push'](_0x1a['shift']());  // 把头部元素搬到尾部
        }
    };
    _0x3c(++_0x2b);
}(_0x4e2b, 0x1));
```

程序一运行，这个 IIFE 会先把数组**旋转**若干次。

> **你静态看到的数组顺序，和运行时的顺序不一样。**

拿静态顺序去查表，自然全错。`examples/07-shift-array.js` 里专门做了对比实验：

```
不执行 IIFE 拿到的数组（错误）：["hello world","log","length"]
    → 索引 0 得到 "hello world"（错！应该是 "log"）
执行 IIFE 后拿到的数组（正确）：["log","length","hello world"]
    → decodeFn(0x0) = "log" ✅
```

### 3.2 破解思路：别心算，让它自己转

**人脑算旋转次数**？

```
++_0x2b 是 2...
while(--_0x4d) 从 1 开始...
所以转 1 次...
等等，到底转几次？
```

本例还算得过来。真实代码里可能是：

```js
_0x3c(_0x2b + 0x1a3 - 0x2f * 0x2);
if (x > 100) { /* 再转一次 */ }
```

**算错一次，全盘皆错。**

所以正确姿势是：

```js
const factory = new Function(`
    ${arrayCode}        // 数组声明
    ${shiftIifeCode}    // ★ 位移 IIFE —— 一起执行！
    ${decodeFnCode}     // 解密函数
    return { arr: ${arrayName}, fn: ${decodeFnName} };
`);
```

**把位移逻辑也执行一遍**，跑完把最终数组拿出来 —— 眼见为实。

> **执行顺序就是依赖顺序**：数组声明 → 位移 IIFE（它修改数组）→ 解密函数。
> 求值工厂里的三行代码，顺序不能乱。

### 3.3 附带收获：认识"函数表达式"这种长相

写 07 时踩到一个坑（已修正，但你要知道）：

```js
// 长相 ①：函数声明
function _0x5f1c(_0x11) { return _0x4e2b[_0x11]; }

// 长相 ②：函数表达式（真实混淆更常用！）
var _0x5f1c = function(_0x11) { return _0x4e2b[_0x11]; };
```

它们在 AST 里是**完全不同的节点**：
- ① 是 `FunctionDeclaration`
- ② 是 `VariableDeclarator`，其 `init` 是 `FunctionExpression`

写收集逻辑时**两种都要认**，否则会漏掉。

> **经验**：混淆器有无数种"写法变体"（函数声明/函数表达式、`function(){}`/箭头函数、
> 立即执行/延迟执行）。写还原脚本时，先想想"这个特征还有哪些写法"，
> 比"写完发现漏了一半"高效得多。

## 4. 两条技术路线：选哪条？

字符串还原有两条路，实战中**通常组合使用**：

| | 运行时求值（本篇） | 静态重写 |
|---|---|---|
| **做法** | 把解密函数跑起来，直接调 | 用人话重写解密逻辑（如"输入索引查表输出"） |
| **优点** | 通杀任意复杂算法，几行搞定 | 不需要执行目标代码，安全 |
| **缺点** | 需要执行代码（有安全风险）；依赖环境时会失败 | 复杂算法要写很久；每次换样本可能重写 |
| **适用** | 解密函数是纯逻辑（本例） | 函数引用了浏览器环境、或对安全性要求高 |

**顶象案例**（见《顶象greenseer AST还原案例分析.md》）用的是**组合拳**：
先尝试 `eval` 求值（快），失败的就跳过；
关键路径再人工静态分析，把算法用 Python/JS 重写（稳）。

> **安全提醒**：`new Function` / `eval` 执行的是**目标代码**。
> 真实逆向中，恶意样本可能借机搞事（检测环境、发请求、写文件）。
> 生产环境请用 `vm` 模块建沙箱，或改用静态重写。
> 本项目里我们执行的是自己提取的纯函数，风险可控。

## 5. 本篇小结

| 概念 | 一句话理解 |
|------|-----------|
| 三件套 | 大数组 + 取值函数 + 索引调用 = obfuscator.io 的招牌 |
| 四步流水线 | 收集 → 求值 → 替换 → 清理 |
| 求值工厂 | `new Function(数组+IIFE+函数)`，让死代码变活函数 |
| 数组位移 | 运行时旋转数组，静态看的下标是错的 → **执行它，别心算** |
| 固定点迭代 | 清理要循环跑到"没有变化"为止 |
| 安全阀 | `try-catch` + 参数必须字面量 + 引用计数检查 |
