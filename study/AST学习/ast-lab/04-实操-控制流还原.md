## 1. 认识对手：代码是怎么被"打碎"的

前面的字符串还原只是"把词认出来"——代码逻辑本身还是看得懂的。
**控制流平坦化（Control Flow Flattening）**不一样，它把逻辑本身搞乱。

原文：

```js
console.log('start');
var a = 1 + 1;
console.log(a);
console.log('end');
```

被平坦化后：

```js
var _0x2f1a = '3|0|1|2'.split('|');       // ① 顺序表：先执行 3，再 0、1、2
var _0x5c = 0x0;                           // ② 指针
while (true) {                             // ③ 调度器
    switch (_0x2f1a[_0x5c++]) {            //    按顺序表取下一个"积木块编号"
        case '0': var _0x1b = 1 + 1; continue;
        case '1': console['log'](_0x1b); continue;
        case '2': console['log']('end'); continue;
        case '3': console['log']('start'); continue;
    }
    break;
}
```

### 为什么这招难缠？

1. **执行顺序和执行位置的顺序无关**：块的物理顺序是 0,1,2,3，
   实际执行顺序是 3→0→1→2，读代码要不停跳转
2. **规模放大**：真实代码有几十上百个块，还互相嵌套
3. **叠加其他混淆**：块内容本身还是字符串数组加密的

> 一篇 2026 年的技术横评里说得很直白：
> 控制流平坦化是"最有效也最难破解"的混淆手段之一。

## 2. 破解思路：找它的"软肋"

### 2.1 关键洞察：混淆器必须"告诉自己要怎么执行"

平坦化把顺序执行变成了"调度"，**那它必须记录调度顺序**——
否则它自己也不知道先执行哪块。

所以它一定把顺序写在某个地方：
- 字符串顺序表：`'3|0|1|2'.split('|')`（本例）
- 数字数组：`[3, 0, 1, 2]`
- 对象映射：`{0: 'a', 1: 'b'}`

**这就是软肋。** 找到那个"记录顺序的地方"，还原就完成了一半。

> 类比：这就像加密——算法可以复杂，但**密钥必须存在某处**给程序自己用，
> 于是也就给了逆向者机会。

### 2.2 还原四步

```
① 找到顺序表，解析出真实执行顺序
② 建立"编号 → 积木块代码"的映射
③ 按顺序表重新排列积木块，替换掉整个调度器
④ 清理调度器残留（指针变量、顺序表变量）
```

对应到 `examples/08-control-flow.js` 的实现：

```js
// ① 解析顺序表：找到 'xxx|yyy'.split('|') 结构
if (!t.isStringLiteral(args[0], { value: '|' })) return;
order = init.callee.object.value.split('|');      // ['3','0','1','2']

// ② 提取积木块：遍历 switch 的每个 case
switchStmt.cases.forEach(c => {
  const blockStmts = c.consequent.filter(s =>
    !t.isContinueStatement(s) && !t.isBreakStatement(s)   // 去掉"调度专用"关键字
  );
  blockMap.set(c.test.value, blockStmts);
});

// ③ 按顺序重排
const newStatements = [];
for (const key of order) {
  newStatements.push(...blockMap.get(key));       // 展开积木块
}
dispatcherPath.replaceWithMultiple(newStatements);  // ★ 替换整个 while
```

结果：

```
还原前：while(true){switch...} + 顺序表 + 指针（11 行）
还原后：
    console['log']('start');
    var _0x1b = 1 + 1;
    console['log'](_0x1b);
    console['log']('end');
```

## 3. 三个必须理解的技术点

### 3.1 为什么要删掉 `continue` 和 `break`？

它们是**调度器专用语法**，不是业务逻辑：

```js
case '0': var _0x1b = 1 + 1; continue;
                             ↑ 意思是"这个块干完了，跳到下一个块"
```

当积木块被拆出来顺序摆放后，`continue` 就失去意义了（它会让程序跳出
当前循环位置），留着会变成语法错误或改变语义。
同理，`switch` 末尾的 `break`（跳出 while）也是调度器的一部分。

> **判断标准：这段代码是在"描述业务"，还是在"描述调度"？**
> 描述调度的，还原后都要删。

### 3.2 为什么用 `replaceWithMultiple` 而不是 `replaceWith`？

Babel 的两个 API 分工：

| API | 用途 |
|-----|------|
| `path.replaceWith(node)` | 一个节点 → 换成一个节点 |
| `path.replaceWithMultiple(nodes)` | 一个节点 → 换成**一串**节点 |

我们要用"4 条语句"替换"1 个 while 语句"，所以用复数版本。

### 3.3 为什么这里的清理还是"循环"

同《03》：删掉调度器后，`_0x2f1a`（顺序表）和 `_0x5c`（指针）
才变成无引用。**依赖关系决定要多轮**。

## 4. 真实场景：比示例难在哪里

本示例是"顺序表"型，是**最简单**的一种。真实世界的变体：

### 变体一：状态变量式（没有顺序表）

```js
var _0xstate = '3';
while (true) {
    switch (_0xstate) {
        case '3': console.log('start'); _0xstate = '0'; break;
        case '0': var a = 1 + 1;        _0xstate = '1'; break;
        case '1': console.log(a);       _0xstate = '2'; break;
        case '2': console.log('end');   return;        // ← 用 return 结束
    }
}
```

**难点**：没有现成的顺序表，得**跟着状态变量"走"一遍**才能串出执行顺序。
做法是模拟执行：从初始状态 `'3'` 出发，读一个 case，看它把状态改成什么，
再跳过去……直到遇到 `return` / `break` 结束。

### 变体二：带条件的跳转

```js
case '2':
    if (x > 5) { _0xstate = '4'; } else { _0xstate = '7'; }
    break;
```

**难点**：这就不是"一条链"了，是**图**（有分支）。
还原时要把"跳转表"变回 `if/else` 结构 —— 本质上是在重建控制流图。

### 变体三：不透明谓词

```js
if (0x1234 > 0x5678) { /* 永远不执行 */ }    // 干扰阅读的垃圾分支
```

**难点**：需要先做常量折叠（《02》）判断出真假，再删死分支。

### 变体四：嵌套平坦化

积木块里还套着小调度器。解法是**递归**处理，或者多轮迭代（一轮解一层）。

> **重要认知**：控制流还原**很难 100% 自动化**。
> 工业界工具（webcrack 等）也是"能自动的自动，不能的留给人工"。
> 实战心态是 **"80% 自动化 + 20% 人工"**：
> 脚本把大部分块理顺，剩下的小部分手动改。
> **不要因为"没做到完美"而否定整个工作。**

## 5. 本篇小结

| 概念 | 一句话理解 |
|------|-----------|
| 平坦化 | 把顺序代码打碎成"积木块 + 调度器"，执行顺序和执行位置解耦 |
| 软肋 | 调度顺序必须被记录下来 → 找到"顺序表/状态转移"就赢了一半 |
| 还原四步 | 找顺序表 → 建块映射 → 按序重排 → 清理调度残留 |
| 删除原则 | 描述"调度"的语法（continue/break）要删，描述"业务"的保留 |
| 现实预期 | 80% 自动化 + 20% 人工，别追求完美 |
