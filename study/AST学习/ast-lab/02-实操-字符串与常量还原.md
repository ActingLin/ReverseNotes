# 实操 02：字符串与常量还原（反混淆的第一战场）

> **配套实例**：`examples/03-delete-debugger.js`、`examples/04-hex-decode.js`、`examples/05-constant-fold.js`
> **读完这篇你会**：干掉反调试、还原伪装的字符串、把混淆器拆碎的常量算回来，
> 并且理解**每一步为什么必须按这个顺序做**。
> **前置**：读完《01-实操-第一个AST脚本.md》，或已经能跑通 `01-hello.js`。

---

## 0. 先看全局：反混淆的处理顺序为什么是固定的？

真实项目里，反混淆不是"想到什么做什么"，而是有一条**依赖链**：

```
① 清反调试        →  不然后面根本没法调试、没法验证
② 还原字面量      →  把 '\x6c\x6f\x67' 变回 'log'，代码才能被"搜到"
③ 常量折叠        →  把 100-8+5 算成 97，让"值"变明确
④ 字符串数组还原   →  解密函数需要"明确的值"当参数（依赖 ③）
⑤ 控制流还原      →  跳转状态需要"明确的字符串/数字"（依赖 ②③④）
⑥ 清理与可读性    →  删垃圾、改格式
```

**为什么不能乱序？** 因为后面的步骤依赖前面步骤的产物。
就像做菜：得先洗菜（②），才能切菜（③），才能下锅（④）。
本篇讲 ①②③，下一篇讲 ④，再下一篇讲 ⑤。

## 1. 第一步：清掉反调试（`examples/03-delete-debugger.js`）

### 1.1 为什么它必须是第一步

假设你要逆向的代码里有这个：

```js
function _0x4f2a() { debugger; }
setInterval(_0x4f2a, 1000);
```

你打开 DevTools，页面每秒中断一次。
**你连代码都跑不起来，怎么调试、怎么验证还原结果对不对？**

所以实战流程永远是：**先让它能调试，再谈还原。**

### 1.2 用 AST 怎么删

```js
traverse(ast, {
  DebuggerStatement(path) {
    path.remove();      // 就这两行
  }
});
```

`debugger;` 对应的节点类型是 `DebuggerStatement`，`path.remove()` 直接摘掉。

### 1.3 为什么不用正则？（这里有真实教训）

```js
code.replace(/debugger;?/g, '')     // ✗ 危险
```

三个原因：

1. **会误伤字符串**：`console.log("debugger")` 里的内容也会被替换
2. **删不干净**：混淆器可能写成 `debugger ;`（有空格）、或者用
   `Function('debugger')()` 动态生成
3. **破坏结构**：如果 `debugger` 是 `if (x) debugger; else y();` 的一部分，
   正则删掉后变成 `if (x) ; else y();` —— 语法错乱

AST 只匹配"语句节点"，字符串里的 `"debugger"` 是 `StringLiteral`，
根本不会被 `DebuggerStatement` visitor 命中。

### 1.4 关键知识点：删除前先检查"引用计数"

删 `debugger` 容易，但**触发它的那套机制**也要清掉：

```js
setInterval(_0x4f2a, 1000);   // ← 触发器，要删
function _0x4f2a() { ... }    // ← 空壳函数，也该删
```

删函数之前必须确认"没人再用它了"，否则会破坏代码：

```js
const binding = path.scope.getBinding(id.name);
if (binding && binding.referencePaths.length === 0) {
  path.remove();     // 引用计数为 0，安全删除
}
```

**`binding.referencePaths` 是什么？**
Babel 在遍历时会自动分析作用域，把"这个名字在哪些地方被引用"
全部记录下来。`length === 0` 就是"没人用了"。

> 这是 AST 反混淆最重要的安全习惯：
> **删除任何声明之前，先看引用计数。**
> 这个模式在后面每篇文档里都会出现。

### 1.5 ★ 踩坑实录：为什么我写成了"两轮遍历" ★

这是实际写这个例子时踩到的坑，非常典型：

```js
// 第一轮：删 debugger + 删 setInterval 调用
// 第二轮：删"已经没人用的空壳函数"
```

**为什么不能一轮搞定？**

traverse 是**按源码顺序**爬的：

```js
function _0x4f2a() { debugger; }     ← 先爬到这儿
setInterval(_0x4f2a, 1000);          ← 后爬到这儿
```

如果在一轮里处理函数节点时检查引用计数，
此刻 `setInterval` 还没被删，函数"看起来"还有引用，于是删不掉。

**更隐蔽的坑**：即使分了两轮，第二轮开始时 Babel 的 scope 信息
**可能还是旧的缓存**（第一轮删掉的引用还记在 `referencePaths` 里）。
必须手动刷新：

```js
traverse(ast, {
  Program(path) {
    path.scope.crawl();     // ★ 强制重新扫描整棵树，重建引用关系
  },
  // ...其他 visitor
});
```

**这两条经验请记住**：
1. **有依赖关系的清理，分多轮做**（真实项目经常跑 5~10 轮）
2. **删过节点之后，scope 可能是脏的，要 `crawl()` 刷新**

## 2. 第二步：还原"字面量伪装"（`examples/04-hex-decode.js`）

### 2.1 混淆器的障眼法

```js
var _0x1234 = 0x1a2b;                     // 十六进制数字
console['\x6c\x6f\x67']('\x68\x69');      // 转义字符串
var s = "你好";                   // Unicode 转义
```

人眼看得出来吗？`\x6c\x6f\x67` 是 `log`、`\x68\x69` 是 `hi`。
但它挡住了两件事：**人眼阅读**和 **Ctrl+F 搜索**。

### 2.2 原理：Babel 存了两份值

这是**必须理解**的机制。解析 `0x1a2b` 时：

```js
{
  type: 'NumericLiteral',
  value: 6699,               // ← 真实值（算好的）
  extra: {
    raw: '0x1a2b',           // ← 源码原文（生成代码时优先用它）
    rawValue: 6699
  }
}
```

`generator` 生成代码时，**如果节点上有 `extra.raw`，就优先输出原文**。
所以还原方法简单到不可思议：

```js
traverse(ast, {
  Literal(path) {          // 别名，一次匹配所有字面量类型
    if (path.node.extra) {
      delete path.node.extra;   // ★ 删掉原文，逼 generator 用 value 重新生成
    }
  }
});
```

> **为什么这是"零风险操作"？**
> `value` 是 Babel 解析时算好的真实值，删 `raw` 只影响"怎么打印"，
> 不影响"是什么"。变换前后代码语义 100% 相同。

### 2.3 第二个关键选项：`jsescOption`

删了 `extra` 之后，你可能发现中文还是转义的：

```js
var s = "你好";     // 明明节点里存的是"你好"
```

这是因为 generator 默认对非 ASCII 字符做转义输出。加一个选项：

```js
generator(ast, { jsescOption: { minimal: true } }).code;
// 输出：var s = "你好";
```

> **这是"还原看起来不彻底"最常见的原因之一** —— 不是没还原成功，
> 是输出来的时候又被转义回去了。顶象案例里也用了这个选项。

### 2.4 顺手做掉：`a["b"]` → `a.b`

字符串还原后，代码会露出很多方括号访问（因为混淆器喜欢统一写成 `a['b']`）：

```js
traverse(ast, {
  MemberExpression(path) {
    if (!path.node.computed) return;                    // 本来就是点号
    if (!t.isStringLiteral(path.node.property)) return;  // 属性不是字符串
    const name = path.node.property.value;
    if (!/^[A-Za-z_$][A-Za-z0-9_$]*$/.test(name)) return; // 非法标识符不能转
    path.node.property = t.identifier(name);
    path.node.computed = false;                          // ★ computed 改 false 就变点号
  }
});
```

**为什么 `computed` 是关键？** `a.b` 和 `a["b"]` 在 AST 里是**同一个节点类型**
（`MemberExpression`），区别只在 `computed` 属性：
- `a.b` → `{ computed: false, property: Identifier }`
- `a["b"]` → `{ computed: true, property: StringLiteral }`

所以"方括号转点号"本质就是改这两个属性。

### 2.5 坑

- **不是所有方括号都能转**：`a["he-llo"]`、`a["123"]` 这种非法标识符转成点号会语法错误
  （所以上面有正则校验）
- **转义不只 `\x` 一种**：还有八进制 `\162`、Unicode `\uXXXX`、`\u{1F600}`，
  但**都是同一个机制**（`extra.raw`），删 `extra` 全部通杀

## 3. 第三步：常量折叠（`examples/05-constant-fold.js`）

### 3.1 混淆器在玩什么把戏

```js
var a = 100 - 8 + 5 - 15;      // 就是 82，偏要写成算式
var b = !0;                    // 就是 true
var c = 'a' + 'b' + 'c';       // 就是 'abc'
var d = 3 === 3 ? 'yes' : 'no'; // 就是 'yes'
```

**为什么混淆器爱这么干？**
因为成本极低（自动转换），收益不小（代码看起来"有逻辑"，实际是障眼法）。

**为什么它挡不住我们？**
因为"表达式求值"是编译器的基本功，Babel 直接白送：
`path.evaluate()`。

### 3.2 核心 API：`path.evaluate()`

```js
const { confident, value } = path.evaluate();
// confident: true  → 我确定结果就是 value（静态可算）
// confident: false → 算不出来（依赖运行时才知道的东西）
```

实操：

```js
traverse(ast, {
  'BinaryExpression|UnaryExpression|ConditionalExpression': {
    exit(path) {                       // ★ 必须 exit，下面解释
      const { confident, value } = path.evaluate();
      if (!confident) return;
      path.replaceWith(t.valueToNode(value));   // JS 值 → AST 节点
    }
  }
});
```

`t.valueToNode()` 是另一个宝藏 API：给它任意 JS 值（数字、字符串、数组、对象），
它自动生成对应的 AST 节点。不用手写 `t.numericLiteral(...)` 那一堆。

### 3.3 ★ 为什么必须写在 exit 里（本篇最重要的知识点）★

看 `100 - 8 + 5 - 15` 的树结构：

```
       (-)                        ← 最外层：算完它才能得到最终值
      /   \
    (+)   15
   /   \
 (+)    5
 /  \
100   8
```

- **写在 enter**：先访问最外层 `(-)`。此时它的右儿子是 `(+)`，
  左儿子是 `15`，整体不是"纯字面量"，**求值可能失败或算错**。
- **写在 exit**：子节点先被处理。轮到最外层时，树已经变成：

```
      (-)
     /   \
   92    15        ← 子节点已经被折叠成字面量了
```

  这时求值 `92 - 15` 直接成功。

**这就是"自底向上"的含义。**（`05-constant-fold.js` 的输出里，
你能看到折叠日志是 `100-8 → 92`、`92+5 → 97`、`97-15 → 82`
一层层从内往外算的）

> **通用规律**：只要你的操作需要"子节点先就位"，就用 exit。
> 这条规律贯穿后面所有复杂变换（控制流还原也用它）。

### 3.4 `evaluate()` 的能力边界

| 能算（confident: true） | 不能算（confident: false） |
|------------------------|--------------------------|
| 字面量运算：`1+2`、`'a'+'b'` | 含变量的：`a + 1`（a 运行时才知道） |
| 逻辑与比较：`!0`、`1 > 2` | 函数调用：`Math.random()`、`atob(x)` |
| 三元（条件是常量） | 全局对象：`window.location` |
| 部分内置属性：`"hello".length` | IIFE：`(function(){return 1})()` |
| 模板字符串（无变量） | 依赖 Date / 随机数的任何东西 |

**注意第二列**——它们不是"做不到"，而是"要换工具"：
- IIFE 和小函数 → 用"求值工厂"执行（见下一篇 `06`）
- 依赖浏览器环境的 → 需要补环境或用 jsdom
- 依赖随机数的 → 静态无解，只能动态 hook

### 3.5 坑

- **必须 exit**（已解释）
- **替换后要防重复处理**：可以在新节点上打标记（如 `node.__folded = true`），
  或者 `path.skip()` 跳过新生成节点的子节点
- **警惕副作用**：`x++` 看着能算，但替换会改变行为。
  只折叠"纯表达式"，别碰带副作用的东西

## 4. 本篇小结

| 步骤 | 干了什么 | 关键 API | 为什么重要 |
|------|---------|---------|-----------|
| ① 清反调试 | 删 `debugger` 和触发器 | `DebuggerStatement` + `binding.referencePaths` | 不然后面没法调试验证 |
| ② 还原字面量 | `\x6c\x6f\x67` → `log` | 删 `extra` + `jsescOption` | 让代码能被搜索、被阅读 |
| ③ 常量折叠 | `100-8+5-15` → `82` | `path.evaluate()` + `exit` | 让"值"变明确，为后续步骤铺路 |

**三条要记住的方法论**：

1. **顺序即依赖**：每个步骤只用前一步的产物，不要跳步
2. **删除先看引用**：`binding.referencePaths.length === 0` 才安全
3. **脏了就刷新**：删过节点后，记得 `scope.crawl()`；多个依赖操作，记得多轮跑
